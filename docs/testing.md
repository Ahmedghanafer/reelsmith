# Testing

The page goes from what runs where, through the helpers the UI tests share, to the tests by part of the app. The app itself is described in `docs/architecture.md`, and how a run is started and read in `docs/operations.md`.

## What runs where

- On Linux, the workflow `Tests` runs `swift test`: the Core tests in `Tests/ReelsmithCoreTests`. On Linux the Engine tests compile to nothing: every file of their target sits inside `#if canImport(AVFoundation)`, but `Tests/ReelsmithEngineTests/Support/MidToneClip.swift`, which holds one function and no test. That is 141 tests on Linux.
- On a Mac, the compile check (the workflow `Compile check`) runs `swift test` on macOS, where the Engine tests run too. Engine tests live in `Tests/ReelsmithEngineTests` and run with `swift test` on macOS only. That is 190 package tests on the hosted Mac. The compile check also builds the UI tests and does not run them.
- UI tests live in `UITests/`, are built by the compile check and run only in the simulator run (the workflow `macOS build`), in one simulator that the run records from before the first test to after the last. The package tests run there too, on macOS, as in the compile check. There are 48 UI tests in nine classes.

What comes back from the simulator run:

- A screenshot kept with the helper `screenshot(_:)` comes back in the artifact `screens` as `<name>.png`.
- A mark set with the helper `mark(_:)` comes back as `<name>.mark.txt` in `screens` and as one line of `recording-index.txt` in the artifact `recording`: the name, a space, and the seconds into `recording.mp4`.
- A file in `screens` can carry another name than the test gave: a character the upload refuses becomes an underscore, and a name that is already taken gets a number, as in `<name>_2.png`. `docs/operations.md` has the rule.
- A failed UI test makes the run red and still brings back the pictures, the recording and the result bundle.
- Before the UI tests the run puts `blue.mov` and `red.mov` into the simulator's photo library and grants the app the right to add to Photos, so no test meets the system's question.
- The run prints the count of videos in the library before and after the UI tests. It grows by six, one for each export that is saved: three in `ExportPanelTests` and three in `WholePathTests`.

## The shared helpers of the UI tests

The helpers in `UITests/Support/Harness.swift` are methods of `XCTestCase`, in an extension marked `@MainActor`. A test class that uses them is marked `@MainActor` too, as in `@MainActor final class TimelineTests: XCTestCase`:

- `func startApp(seed: String?, language: String = "en", playhead: Int? = nil, exportFails: Bool = false) -> XCUIApplication` starts the app and returns it right after the launch, without waiting for any screen. `seed` is the name of a seed such as `"two-clips"`, or nil for a start with no seed. `language` is `"en"`, `"ar"` or `"sv"` and is passed as `-AppleLanguages (<code>)` and `-AppleLocale <code>`. `playhead` is in ticks, 600 a second.
- `func waitForTheEditor(_ app: XCUIApplication)` waits for the editor after a seeded start, as described below.
- `func screenshot(_ name: String)` keeps a picture of the screen under the given name, also when the test passes. A name is a prefix, two digits and what the picture shows. The prefix of the newer pictures is their topic, as in `picture-01-blue-fills`, and that of the older ones is a fixed label, as in `m1-10-export-03-saved`.
- `func mark(_ name: String)` marks the start of a stretch of the recording: a text attachment `<name>.mark.txt` with the clock second of the call, whole seconds since 1970.

The names of the screenshots and the marks, and the first words of the lines a test prints, are fixed text in the test files. This page gives them as they are written there, so that a file of a run and a line of its log can be found.

A control is found by its identifier, whatever kind of element it is: `app.descendants(matching: .any)["editor.root"]`.

After a seeded start the editor is not there at once. The first seeded start in a fresh simulator writes the seed's clips before the editor opens, and every later start finds them. So every test calls `waitForTheEditor(app)` of `UITests/Support/Harness.swift` after a seeded start and before it touches anything. It waits for `editor.root`, expected within 60 seconds and failing only at 180, and prints a line that starts with `m1-18-held-runner: editor.root after` with the seconds it took. Then, unless `editor.seedInfo` names 0 clips, it waits until `editor.clip.1` has a frame with a width and a height, expected within 1 second and failing only above 3, and prints a line that starts with `m1-18-held-runner: waited`, because a tap on a block is placed from its frame. The wait for `editor.root` counts its 180 seconds from the call. The printed seconds of the wait for the frame, and of the waits after a tap in the test files, include the first read, and the limit of these counts from the end of that read, so a slow first read still gets a second one. Three waits count their limit from their start: the waits of `ExportPanelTests`, the wait for a share in `PictureTests` and the wait after the drag in the Arabic test of `TimelineTests`. Until the store is set the content of the slot `start` is on screen. A clip that could not be written is logged by the app with `NSLog` as a line that starts with `seed start:`.

## The picture probe

`UITests/Support/Probe.swift` holds one helper, a method of `XCTestCase` in an extension marked `@MainActor`, beside `startApp`, `screenshot` and `mark`:

    func share(of colour: (r: Int, g: Int, b: Int), in element: XCUIElement) -> Double

It takes a screenshot of the screen, draws it into an sRGB bitmap with 8 bits a channel in the order red, green, blue, alpha, and reads every fourth pixel of every fourth row inside the element's frame. The frame is in points and the bitmap in pixels: the scale is the pixel width of the screenshot divided by its width in points. The answer is the share, from 0 to 1, of the pixels read that lie within 48 of 255 per channel of the colour. The colour is a plain tuple, because the UI test target does not depend on the package. A probe that cannot make its bitmap, or finds no pixel of the element on the screen, fails the test and answers 0.

A test compares a share with "more than" or "less than" a number and never with an exact value: the probe cannot tell a shade inside the tolerance from the right one. No element says when a frame is drawn, so `PictureTests` asks again until the share it waits for is met, prints a line that starts with `picture: waited` with the seconds it waited, and gives up only above three times the expected seconds.

`UITests/PictureTests.swift` holds the previews with it, every start with a playhead and paused. On `two-clips-wide` at 600 ticks blue is above 0.9 and red and green are below 0.05. At 3000 ticks red is above 0.2 and below 0.45, black above 0.5 and blue below 0.05, since red covers 0.316 of the canvas. On `two-clips` at 600 ticks blue is above 0.2 and below 0.45 and black above 0.5, and at 3000 ticks red is above 0.9 and blue below 0.05. On `three-clips` at 4800 ticks green is above 0.9 and red and blue are below 0.05. The expected wait for a frame is 3 seconds. Screenshots: `picture-01-blue-fills`, `picture-02-red-with-bars`, `picture-03-portrait`.

### The guard of the edits

`Tests/ReelsmithCoreTests/TrackGuardTests.swift` guards the edits as a whole and runs on Linux. It changes no product code. Its two tests of runs test no single edit: what each edit does is held by `EditActionsTests.swift`.

- Two tests play 1000 runs of 50 actions each, one from `Seed.threeClips` and one from a project of two media that are 1219 and 2417 ticks long, so not whole frames. The actions come from a random source in the file itself (SplitMix64, whole number arithmetic only) with the start numbers 1 to 1000, so a run is the same on every platform and every time.
- After every action the state must be valid (each clip inside its source, each length whole frames and at least `minimumClip`, the playhead a whole frame inside the project, the selection a clip of the project or none), `renderPlan(for:)` must not throw and must give a plan as long as the project whose segments touch and lie inside their media, and a `split` or `deleteSelected` must change the state exactly when `canSplit` or `canDelete` was true.
- The run from the seed also fails when a kind of action was never sent. The kinds are the cases of the enum `Kind` in the file: every case of `EditorAction`, amounts past each limit, clip ids that are not in the project, and a project that became empty.
- A failure names the start number, the number of the action and what was broken, and prints the actions of that run. To play it again, send those actions to `reduce` one by one from the start state. The tests stop at the first run that fails.
- Two small tests hold single edits: that a trim of a clip before the playhead leaves the playhead at its time, and that a `trimEnd` that rounds to nothing still pauses.

Changing a weight, a range or the media list in the file changes every run, so the count of each kind must be looked at again.

## The Engine tests

The tests make their clips in folders they make under the temporary folder, with `writeTestClip`, with `writeQuarterClip(named:firstFrame:to:)` and, for the one clip in high dynamic range, with `writeHighDynamicRangeClip(to:)` inside `CompositorTests.swift`. No media file is committed. Sizes, frame counts and lengths are exact, a colour matches within 24 of 255 per channel where no other bound is given.

The helpers in `Tests/ReelsmithEngineTests/Support/MediaReading.swift` read a file back. Each takes the file's URL:

- `pixel(of:at:x:y:)`: the colour of one pixel of the stored picture as an `RGB`, x from the left and y from the top, in the frame shown at a Core `Time`. The turn of the file is not applied.
- `frameCount(of:)`: the number of picture frames, counted without decoding.
- `soundPeak(of:)`: the peak of the first sound track, from 0 to 1 of full scale.
- `storedSize(of:)`: width and height of the picture as stored.
- `tracks(of:)`: one `TrackFacts` per track with `kind` ("vide" or "soun"), `coding` ("avc1" for H.264, "lpcm" for uncompressed sound, and an AAC track reads back as "aac " with a trailing space), `duration`, and for sound `sampleRate`, `channels` and `bitsPerSample`.
- `fileType(of:)`: the major brand the file starts with, "qt  " for a QuickTime movie.
- `colourProperties(of:)`: the primaries, transfer function and matrix the picture track reports, by the platform's names.
- `storedTransform(of:)`: the six numbers a, b, c, d, tx, ty of the picture track.

Two more files of `Tests/ReelsmithEngineTests/Support` make clips that are no test clip of Core:

- The mid tone clip is made by `midToneClip()` in `Tests/ReelsmithEngineTests/Support/MidToneClip.swift`: 1920 by 1080, grey 128, 128, 128 on the left and 64, 160, 96 on the right, written by `writeTestClip` when a test asks, and not part of `TestClip.all`.
- The clip of four quarters is written by `writeQuarterClip(named:firstFrame:to:)` in `Tests/ReelsmithEngineTests/Support/QuarterClip.swift`, with its colours in `QuarterClip`: 1920 by 1080, one second of frames of which the first stands at `firstFrame`.
