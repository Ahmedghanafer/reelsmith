# Testing

The page goes from what runs where, through the helpers the UI tests share, to the tests by part of the app. The app itself is described in `docs/architecture.md`, and how a run is started and read in `docs/operations.md`.

## What runs where

- On Linux, the workflow `Tests` runs `swift test`: the Core tests in `Tests/ReelsmithCoreTests`. On Linux the Engine tests compile to nothing: every file of their target sits inside `#if canImport(AVFoundation)`, but `Tests/ReelsmithEngineTests/Support/MidToneClip.swift`, which holds one function and no test, and `TextPictureTests.swift` and `TextExportTests.swift`, which sit inside `#if canImport(CoreText)`. That is 396 tests on Linux.
- On a Mac, the compile check (the workflow `Compile check`) runs `swift test` on macOS, where the Engine tests run too. Engine tests live in `Tests/ReelsmithEngineTests` and run with `swift test` on macOS only. That is 544 package tests on the hosted Mac. The compile check also builds the UI tests and does not run them.
- UI tests live in `UITests/`, are built by the compile check and run only in the simulator run (the workflow `macOS build`), in one simulator that the run records from before the first test to after the last. The package tests run there too, on macOS, as in the compile check. There are 148 UI tests in twenty-four classes.

What comes back from the simulator run:

- A screenshot kept with the helper `screenshot(_:)` comes back in the artifact `screens` as `<name>.png`.
- A mark set with the helper `mark(_:)` comes back as `<name>.mark.txt` in `screens` and as one line of `recording-index.txt` in the artifact `recording`: the name, a space, and the seconds into `recording.mp4`.
- A file in `screens` can carry another name than the test gave: a character the upload refuses becomes an underscore, and a name that is already taken gets a number, as in `<name>_2.png`. `docs/operations.md` has the rule.
- A failed UI test makes the run red and still brings back the pictures, the recording and the result bundle.
- Before the UI tests the run puts `blue.mov` and `red.mov` into the simulator's photo library and grants the app the right to add to Photos, so no test meets the system's question.
- The run prints the count of videos in the library before and after the UI tests. It grows by eleven, one for each export that is saved: one in `ExportChoiceTests`, three in `ExportPanelTests`, two in `WholeExportPathTests`, three in `WholePathTests`, one in `WholeTextPathTests` and one in `WholeSoundPathTests`.

The simulator run has three kinds, started as `docs/operations.md` tells. With no input it runs every UI test on one machine. With classes named it is a part run: the named classes and the smoke set, five tests listed as `SMOKE_TESTS` in `.github/workflows/macos.yml` (a start with no seed, a start on a seed, the first frame of the preview, a split and a delete on the strip, an export to the saved panel). A part run proves its classes and that the app still starts, shows a picture, edits and saves, and says nothing about the other tests, so the count of videos grows only by the exports it ran. A split run deals every test class into three groups on three machines and proves the same as the run on one machine, with the eleven saved videos counted in the groups that hold the six exporting classes. The line `UI tests of this run:` in the log of layer 4 and in the Summary tells which kind a run was.

## The shared helpers of the UI tests

The helpers in `UITests/Support/Harness.swift` are methods of `XCTestCase`, in an extension marked `@MainActor`. A test class that uses them is marked `@MainActor` too, as in `@MainActor final class TimelineTests: XCTestCase`:

- `func startApp(seed: String?, language: String = "en", playhead: Int? = nil, exportFails: Bool = false) -> XCUIApplication` starts the app and returns it right after the launch, without waiting for any screen. `seed` is the name of a seed such as `"two-clips"`, or nil for a start with no seed. `language` is `"en"`, `"ar"` or `"sv"` and is passed as `-AppleLanguages (<code>)` and `-AppleLocale <code>`. `playhead` is in ticks, 600 a second.
- `func waitForTheEditor(_ app: XCUIApplication)` waits for the editor after a seeded start, as described below.
- `func screenshot(_ name: String)` keeps a picture of the screen under the given name, also when the test passes. A name is a prefix, two digits and what the picture shows. The prefix of the newer pictures is their topic, as in `picture-01-blue-fills`, and that of the older ones is a fixed label, as in `m1-10-export-03-saved`.
- `func mark(_ name: String)` marks the start of a stretch of the recording: a text attachment `<name>.mark.txt` with the clock second of the call, whole seconds since 1970.

The names of the screenshots and the marks, and the first words of the lines a test prints, are fixed text in the test files. This page gives them as they are written there, so that a file of a run and a line of its log can be found.

A control is found by its identifier, whatever kind of element it is: `app.descendants(matching: .any)["editor.root"]`.

After a seeded start the editor is not there at once. The first seeded start in a fresh simulator writes the seed's clips before the editor opens, and every later start finds them. So every test calls `waitForTheEditor(app)` of `UITests/Support/Harness.swift` after a seeded start and before it touches anything. It waits for `editor.root`, expected within 60 seconds and failing only at 180, and prints a line that starts with `m1-18-held-runner: editor.root after` with the seconds it took. Then, unless `editor.seedInfo` names 0 clips, it waits until `editor.clip.1` has a frame with a width and a height, expected within 1 second and failing only above 3, and prints a line that starts with `m1-18-held-runner: waited`, because a tap on a block is placed from its frame. The wait for `editor.root` counts its 180 seconds from the call. The printed seconds of the wait for the frame, and of the waits after a tap in the test files, include the first read, and the limit of these counts from the end of that read, so a slow first read still gets a second one. Four waits count their limit from their start: the waits of `ExportPanelTests`, the wait for the saved panel in `ExportChoiceTests`, the wait for a share in `PictureTests` and the wait after the drag in the Arabic test of `TimelineTests`. Until the store is set the content of the slot `start` is on screen. A clip that could not be written is logged by the app with `NSLog` as a line that starts with `seed start:`. In the simulator run the first seeded start is the warm start of layer 4, before the first test (`docs/operations.md`). When it has written every clip and built the editor, no start inside a test writes one, and the first test's line is expected to show a start like any later one. When it has not, a start inside a test can still write clips of its seed and be the first to build the editor, and the helper's 60 and 180 seconds are for that.

## The picture probe

`UITests/Support/Probe.swift` holds one helper, a method of `XCTestCase` in an extension marked `@MainActor`, beside `startApp`, `screenshot` and `mark`:

    func share(of colour: (r: Int, g: Int, b: Int), in element: XCUIElement) -> Double

It takes a screenshot of the screen, draws it into an sRGB bitmap with 8 bits a channel in the order red, green, blue, alpha, and reads every fourth pixel of every fourth row inside the element's frame. The frame is in points and the bitmap in pixels: the scale is the pixel width of the screenshot divided by its width in points. The answer is the share, from 0 to 1, of the pixels read that lie within 48 of 255 per channel of the colour. The colour is a plain tuple, because the UI test target does not depend on the package. A probe that cannot make its bitmap, or finds no pixel of the element on the screen, fails the test and answers 0.

A test compares a share with "more than" or "less than" a number and never with an exact value: the probe cannot tell a shade inside the tolerance from the right one. No element says when a frame is drawn, so `PictureTests` asks again until the share it waits for is met, prints a line that starts with `picture: waited` with the seconds it waited, and gives up only above three times the expected seconds.

`UITests/PictureTests.swift` holds the previews with it, every start with a playhead and paused. On `two-clips-wide` at 600 ticks blue is above 0.9 and red and green are below 0.05. At 3000 ticks red is above 0.2 and below 0.45, black above 0.5 and blue below 0.05, since red covers 0.316 of the canvas. On `two-clips` at 600 ticks blue is above 0.2 and below 0.45 and black above 0.5, and at 3000 ticks red is above 0.9 and blue below 0.05. On `three-clips` at 4800 ticks green is above 0.9 and red and blue are below 0.05. The expected wait for a frame is 3 seconds. Screenshots: `picture-01-blue-fills`, `picture-02-red-with-bars`, `picture-03-portrait`.

Two tests of that file hold that an edit never leaves the picture area black. Every read starts only when the call of the tap or the drag has come back.

The first, on `three-clips` at 4800 ticks, one second into the green clip, which fills the area, makes four edits. After each of the first three it reads the share of green as often as the probe can for half a second and prints a line `picture: <count> reads in <seconds> seconds after <the edit>, the share of green from <lowest> to <highest>`. The trim: the green block is selected and its end handle dragged 30 points to the left, every read finds green above 0.9, and the block is then narrower than 120 points. The split, at the playhead: every read above 0.9. A delete of the first part of green, after which the playhead stands on the end of the project and the picture is the last frame of the second part: every read above 0.9. In these three the picture has the same colour before and after, so nothing tells the test when the new item went into the player: when a build takes longer than the half second, those reads end before it. The fourth edit is a delete of the rest of green, after which the picture is the last frame of red, which fills the area too. After it black and red are read in turn until red is above 0.9, expected within 3 seconds and given up above 9, and every read of black is below 0.1.

The second, on `three-clips` at 2400 ticks, where red is under the playhead, selects the blue block and deletes it. The playhead stays at "00:04" and green is under it now, so the picture changes from one clip that fills the area to another. Black and green are read in turn until green is above 0.9, with the same limits, and the share of red read after that is below 0.05. The playhead stands exactly on the cut between red and green there, so this is also the test of which clip the picture shows on a cut after an edit. A green run of it does not prove that: the fault it was seen with came once in many runs (`docs/architecture.md`, The preview).

Both reads until a colour print a line `picture: <count> reads of black in <seconds> seconds from <the edit> to <colour>, the highest share of black <share>, <colour> <share>, expected 3.0, the app lets go of the old picture after 15 seconds`. The 15 is typed into the test and is the limit of the app (`docs/architecture.md`, The preview). It is past the 9 seconds, so an old picture that only that limit took away fails the wait for the colour.

What these tests cannot see: a read takes a screenshot, about a third of a second in the simulator run, so a black area that lasts one frame can fall before the first read or between two reads, and no read tells whether an old picture lay over the layer. Two more proofs close that. The app's lines in `simulator-log.txt` that start with `old picture`: every edit of these tests shows `old picture laid, item <number>` and then `old picture taken away after <milliseconds> ms, item <number>: the layer reported ready`. A line `old picture not laid` after an edit, or a taking away by `the limit of 15 seconds`, means the picture was not kept or not let go as meant. And the recording, between the marks `picture-01-edit-trim`, `picture-02-edit-split`, `picture-03-edit-delete`, `picture-04-edit-delete-last` and `picture-05-edit-delete-before`, each set just before its edit. Screenshots: `picture-04-after-trim`, `picture-05-after-split`, `picture-06-after-delete` (green fills the area in all three), `picture-07-red-after-delete` (red fills it) and `picture-08-green-after-delete` (green fills it, two blocks).

### The text guard

`Tests/ReelsmithCoreTests/TextGuardTests.swift` guards the clip actions and the text actions together and runs on Linux. It changes no product code and tests no single edit: what each text action does is held by `TextEditsTests.swift`. The text guard is where text actions are drawn: the guard of the edits, below, sends none.

- One test plays 1000 runs of 50 actions from each of the three seeds `text-wide`, `text-box-wide` and `three-clips`, 3000 runs in all. A text seed starts with its text selected, as a start of the app on it does. The actions come from a random source in the file itself (SplitMix64, whole number arithmetic only) with the start numbers 1 to 1000 for each seed, so a run is the same on every platform and every time. 22 actions in 47 are clip actions and the others are text actions.
- The values drawn go past every limit and onto it: a size from minus 24 to 1000, a line spacing from minus 1 to 3, a centre outside each edge of the canvas and on each edge, an angle from minus 780 to 780 and in tenths around 0, trims by ten thousand ticks either way, which is more than the length of each seed, by at most 60 ticks and by a negative amount, clip ids and text ids that are not in the project, and the strings of the list `strings`: empty, spaces only, with a line break, the Arabic line of `text-wide` and plain words.
- After every action the state must be valid, for the clips as in the guard of the edits and for the texts: every text id used once, every range at a whole frame not below zero and whole frames of at least `minimumText` long, every size from 16 to 400, every centre inside the canvas with the edge inside, every rotation above minus 180 and at most 180, the selected text a text of the project or none, at most one of a clip and a text selected, and a blank text only while it is selected.
- After every action `renderPlan(for:)` must not throw and must give a plan as long as the project whose segments touch. Its layers must be exactly the texts that are not blank and have a range, in the order of the project. Each layer must start at a whole frame not below zero, be longer than zero, end inside the plan, have the start and the length of `range(of:)` of its text, carry its string, centre, rotation and style, and have the line width of the canvas width times `wrapShare`.
- After every action `textInfo` must be "none" exactly when no text is selected, and else ten fields with one space between them, the ninth "hidden" exactly when the selected text has no range.
- What an action may do: a clip action leaves the texts equal, but for a blank text that lost its selection, which is gone. A `deleteSelected` with a text selected finds `canDelete` true, removes exactly that text and leaves the clips equal. An `add` on a project with a clip gives an id higher than every text id seen earlier in the run. A text action on a text id that is not in the project, an `add` on an empty project, a trim of a text with no range and a `trimEnd` of a text whose seen range is shorter than `minimumText` return a state equal to the one before.
- The test fails when a kind of action was never drawn. The kinds of text actions are the cases of the enum `TextKind` in the file: each case of `TextAction` in each of its outcomes (done, held at a limit, a text id that is not in the project, nothing to do) and each value past a limit or on it. The kinds of clip actions are the cases of `ClipKind`: every other case of `EditorAction` but `sound`, for which the function that names the kind of a clip action answers none, `deleteSelected` with and without a selected text, and a clip id that is not in the project.
- A failure names the seed, the start number, the number of the action and what was broken, and prints the actions of that run up to the one that failed. To play it again, send those actions to `reduce` one by one from the state of the seed, with `selectedText` set to the seed's `selectedText`. The test stops at the first run that fails.

Changing a weight, a range or one of the lists in the file changes every run, so some kind may no longer be drawn. The rarest kinds are a trim of a text whose seen range is shorter than `minimumText`, which needs a clip edit that ends the project one or two frames after the start of a text, and an `add` on an empty project. When one of them is no longer drawn the test fails and names it.

### The sound guard

`Tests/ReelsmithCoreTests/SoundGuardTests.swift` guards the clip, text and sound actions together and runs on Linux. It changes no product code and tests no single edit: what each sound action does is held by `SoundEditsTests.swift`. The sound guard is where sound actions are drawn: neither the text guard nor the guard of the edits sends one.

- One test plays 1000 runs of 50 actions from each of the three seeds `music-wide`, `text-wide` and `three-clips`, 3000 runs in all. A run starts as a start of the app on the seed does: on `music-wide` with `showsSound` true, on `text-wide` with its text selected. The actions come from a random source in the file itself (SplitMix64, whole number arithmetic only) with the start numbers 1 to 1000 for each seed, so a run is the same on every platform and every time. 21 actions in 50 are clip actions, 9 are text actions and 20 are sound actions.
- The values drawn go past every limit of the sound actions: volumes below 0 and above 1, a number that is not finite (not a number and both infinities), starts below zero, above the largest start and not on a whole frame, fades below zero, above 3000 ticks and not on a whole frame, and the value the project already has. `setMusic` is given `long-tone`, `short-tone`, a file of 500 ticks, a file of 900 ticks and a file with no length.
- After every action the state must be valid: as in the text guard for the clips, the playhead and the texts, and as seam P adds, each volume from 0 to 1, the start of the music a whole frame from zero to `largestStart`, both fades whole frames from zero to `maximumFade`, a file of a length above zero, at most one of `selection`, `selectedText` and `showsSound`, and `showsSound` false on an empty project. `heardMusic`, `soundInfo` (three or six fields, the third "hidden" exactly when there is music and no clip) and `canSetMusicStart` must follow the project.
- After every action on a project with a clip `renderPlan(for:)` must not throw, the volume of the clips in the plan must be 0 when muted and the stored value otherwise, and the music layer must exist exactly when `heardMusic` does. The layer must start at the start of the music, be `heardMusic` long, end inside the plan and inside its file, have each fade equal to the stored one cut to half its length, and carry the id, the file name and the volume of the music.
- What an action may do: a clip action or a text action leaves the volume of the clips, the mute and the music equal. `open` on a project with a clip shows the panel and clears both selections. A `select` of a clip or a text of the project, an `add` of a text on a project with a clip and `clearSelection` leave the panel closed. A sound action with nothing to do returns a state equal to the one before, the playing flag included: `open` on an empty project, an action on the music with no music, a number that is not finite, the value the project already has and a file with no length. Every other sound action but `open` that changes the state leaves the state not playing.
- The test fails when a kind was never drawn. The kinds of sound actions are the cases of the enum `SoundKind` in the file: each case of `SoundAction` in each of its outcomes (done, held at a limit, nothing to do) and each value past a limit. The cases of `EditorAction` and `TextAction` are the cases of `ActionCase`, and each must be sent too.

### The level of a pitch

Sound is proven by numbers. `Tests/ReelsmithEngineTests/Support/SoundReading.swift` holds the two readers every sound test uses, and no test writes another.

- `toneLevel(of:hertz:from:to:)` reads a file: the first channel of its first sound track, as 16 bit samples at the rate of the track. `mixedToneLevel(of:mix:hertz:from:to:)` reads all sound tracks of an asset mixed with an audio mix, with no export.
- A level is the size of the part of the sound that swings at one pitch, from 0 to 1 of full scale: a sine with a peak of 0.5 reads 0.5 at its own pitch and nothing at another. Each read is printed.
- A window is given in ticks and is a whole number of tenths of a second, so of 60 ticks. Another window fails the test that asked for it, and so does a window the sound does not fill, a file with no sound track, named in the error, and an asset with none. Pitches are multiples of 10 Hz, so a window holds whole periods at 44100 and at 48000 samples a second.
- A level is asserted within 15 percent of its expected value, or as above or below a number. Silence reads below 0.02.
- Inside a ramp of the mix, `mixedToneLevel` reads lower than the exported file does. A held volume may be asserted through it. The size of a fade is asserted on an exported file.
- `Tests/ReelsmithEngineTests/ToneLevelTests.swift` holds the readers and the ground the mix stands on: a tone at two sample rates and silence, the export of the seed `two-clips` at 440 Hz inside both clips, and two sound tracks under a mix that come out of an export as one track at the levels of the mix, the second also as stereo at 48000 over a mono first at 44100. Its tones are written by the test into a temporary folder.
